3. ARQUITECTURA DE ROLES (ID TOKEN CLAIMS EN AZURE AD)
--------------------------------------------------------------------------------
¿Es posible extraer el claim de roles ahora sin tocar el backend?
SÍ. Los roles son emitidos directamente por Azure Entra ID en el ID Token (JWT)
durante el login del usuario en el frontend:
- Ubicación: `account.idTokenClaims.roles` (array de strings: ["Admin"], ["Recepcionista"], etc.).
- En el frontend se implementó el hook `useUserRole` (src/hooks/useUserRole.ts):
  * Lee y mapea los claims nativos de Azure.
  * Provee un selector de roles para modo desarrollo/evaluación (guardado en sessionStorage/localStorage),
    permitiendo probar todas las pantallas y restricciones de inmediato sin esperar
    la configuración manual de App Roles en el portal de Azure.
  * El backend de Spring Boot solo consumirá estos mismos roles más adelante
    para validar `@PreAuthorize("hasRole('Admin')")`.

4. ARCHIVOS MODIFICADOS Y CREADOS
--------------------------------------------------------------------------------

A. Variables de Entorno (Frontend/.env)
   - VITE_AZURE_CLIENT_ID: Identificador de la App Cliente en Azure AD.
   - VITE_AZURE_TENANT_ID: Identificador del Tenant en Azure AD.
   - VITE_AZURE_REDIRECT_URI: URI de redirección post-login (http://localhost:5173).
   - VITE_AZURE_API_CLIENT_ID: ID de la App API en Azure.
   - VITE_AZURE_API_SCOPE: Ámbito de acceso (api://TU_API_CLIENT_ID/access_as_user).
   - VITE_API_GATEWAY_URL: Base URL del AWS API Gateway (https://api-gateway-url.aws.com/v2).

B. Configuración de MSAL (Frontend/src/authConfig.ts)
   - Configuración de `msalConfig` con cache en "localStorage" para persistencia cross-tab.
   - `navigateToLoginRequestUrl: false` para evitar navegación redundante tras volver de Azure AD.
   - Omitido `storeAuthStateInCookie` debido a incompatibilidad con MSAL v5.
   - Configuración de `loginRequest` con scopes hacia el API.
   - Exportación de la instancia singleton `msalInstance`.

C. Entrypoint y Sincronización Singleton (Frontend/src/main.tsx)
   - Se importa `msalInstance` desde authConfig para evitar instancias desincronizadas.
   - Registro de callback reactivo para `LOGIN_SUCCESS` y `ACQUIRE_TOKEN_SUCCESS` que
     establece inmediatamente la cuenta activa (`setActiveAccount`).
   - Procesamiento de redirección al inicio mediante `handleRedirectPromise()`.

D. Cliente Axios con Interceptor (Frontend/src/api/axiosClient.ts)
   - Interceptor de petición que adquiere silenciosamente el token (`acquireTokenSilent`)
     y añade la cabecera `Authorization: Bearer <accessToken>`.

E. Componentes de Seguridad y Navegación
   - `src/hooks/useUserRole.ts`: Hook para extracción de roles y control de privilegios.
   - `src/components/ProtectedRoute.tsx`: Guard de ruta que valida login y roles permitidos.
   - `src/components/Navbar.tsx`: Barra de navegación con logo, selector de rol de prueba,
     insignia de rol activo y botón de cerrar sesión.

F. Las 6 Pantallas del Caso (Frontend/src/pages/)
   1. `LoginPage.tsx` (/login):
      Acceso público. Botón corporativo "Iniciar sesión con Microsoft" mediante flujo nativo
      por redirección directa (`loginRedirect`). Indicador visual de autenticación y spinner
      durante la resolución de la redirección.
   2. `DashboardPage.tsx` (/dashboard):
      Todos los autenticados. Vista adaptativa según rol (Admin: ocupación y KPIs;
      Recepcionista: check-in/out del día; Huésped: mis reservas; Auditor: resumen)
      e integración interactiva del botón "Obtener Datos vía API" (Diagrama de Secuencia).
   3. `ReservationsPage.tsx` (/reservations):
      Roles: Admin, Recepcionista, Huésped.
      CRUD de reservas, creación de reservas y máquina de estados con validación de regla
      de negocio: "No se puede hacer check-in sin CONFIRMAR".
      Ciclo: CREADA -> CONFIRMADA -> CHECKIN_PENDIENTE -> EN_ESTADÍA -> CHECKOUT / CANCELADA.
   4. `CatalogPage.tsx` (/catalog):
      Roles: Admin, Recepcionista.
      Listado y gestión de unidades (habitaciones/cabañas), tarifas por noche, capacidad
      y control de disponibilidad.
   5. `ReportsPage.tsx` (/reports):
      Roles: Admin.
      Panel de KPIs en tiempo real: ocupación, tiempo de ciclo promedio, reservas por hora
      y top de unidades más demandadas.
   6. `AuditPage.tsx` (/audit):
      Roles: Admin, Auditor.
      Timeline inmutable de eventos de reservas (solo lectura), con filtros por usuario,
      ID de reserva y tipo de evento (CREACION, CONFIRMACION, CHECK_IN, CHECK_OUT).

G. Enrutador Principal (Frontend/src/App.tsx)
   - Configurado con `BrowserRouter`, `Routes` y `Route` aplicando `ProtectedRoute`.

6. OPTIMIZACIÓN DEL FLUJO DE INICIO DE SESIÓN (DIAGNÓSTICO Y SOLUCIÓN)
--------------------------------------------------------------------------------
A. Causa Raíz del Problema Anterior:
   1. Bucle de Popups:
      - Anteriormente `LoginPage.tsx` utilizaba `instance.loginPopup(loginRequest)`
        con `redirectUri` apuntando a `http://localhost:5173`.
      - Al completarse el inicio de sesión en Microsoft, la ventana emergente era
        redirigida a la raíz de la SPA, cargando la aplicación React entera dentro
        de la pequeña ventana del popup.
      - En esa ventana emergente, `main.tsx` ejecutaba `handleRedirectPromise()`,
        lo cual borraba el hash (#code=...) de la URL.
      - En consecuencia, la ventana padre nunca se enteraba de la finalización del
        popup y quedaba en estado de espera permanente.
      - A su vez, el popup volvía a renderizar la pantalla de LoginPage; si el
        usuario pulsaba iniciar sesión allí, se abría un segundo popup, creando un
        bucle anidado de ventanas.

   2. Bloqueo del Botón y Retraso de 1 Minuto:
      - La promesa de `loginPopup` en la ventana principal quedaba bloqueada
        esperando el hash hasta que se cumplía el `windowHashTimeout` por defecto
        de MSAL (exactamente 60 segundos / 1 minuto).
      - El botón quedaba congelado mostrando "Cargando..." durante todo ese minuto.
      - Solo al vencer el timeout de 60s, la promesa fallaba y la ventana leía los
        tokens ya guardados en `localStorage` por el popup, permitiendo finalmente
        entrar al Dashboard con 1 minuto de retraso.

B. Solución Aplicada:
   1. Migración a `loginRedirect(loginRequest)`:
      - Flujo nativo recomendado por Microsoft para SPAs React.
      - Redirección limpia en la misma pestaña hacia Microsoft Entra ID.
      - 0 popups emergentes, 0 bloqueos por navegadores modernos.
      - Retorno directo a `http://localhost:5173` procesado en < 1 segundo por
        `handleRedirectPromise()` en `main.tsx`.
   2. Experiencia de Usuario (UX) Optimizada:
      - Estado `isAuthenticating` (`HandleRedirect` / `Startup`) que muestra un
        spinner estilizado "Autenticando con Microsoft Entra ID..." mientras se
        resuelven los claims.
      - Transición instantánea al Dashboard una vez autenticado sin recargas
        innecesarias (`navigateToLoginRequestUrl: false`).
   3. Integridad de Tokens JWT y AWS API Gateway:
      - Se mantiene inalterado el esquema de tokens: los scopes de API
        (`apiTokenRequest`), la adquisición silenciosa (`acquireTokenSilent`)
        y la inyección del header `Authorization: Bearer <token>` en `axiosClient.ts`
        siguen operando con total normalidad.
